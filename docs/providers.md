# Providers and operations

## Providers

| Configuration type | Implementation and prerequisites |
| --- | --- |
| `remote` | Authenticated HTTPS implementing [protocol v1](../REMOTE_PROVIDER_PROTOCOL.md). Uses `endpoint` and `token_env`. `allow_http` is an explicit development option. |
| `docker` | Local Docker Engine on Linux or Docker Desktop on macOS, accessed over a Unix socket. Runs c2j directly without host mounts or a helper. Applies CPU/memory/swap limits when available; otherwise warns at startup and runs without those limits. One admission owner per daemon. |
| `cloudrun` | Cloud Run Jobs REST v2. Requires `project`, `region`, and optionally `service_account`. Uses native Google Application Default Credentials (attached service account, credential file, or federation). Optional `token_env` overrides discovery. |
| `ecs` | Standalone Fargate tasks via the AWS SDK for Go v2. Requires `region`, `cluster`, `subnets`, `execution_role`, and `supervisor_path`; optional `task_role`, `security_groups`, and `public_ip`. Uses the AWS credential chain, including environment credentials and task/instance roles. |
| `azurejobs` | Manual Container Apps Jobs REST API `2025-07-01`. Requires `subscription`, `resource_group`, `environment_id`, and `region`. Uses native Azure environment, workload-identity, or managed-identity credentials. Optional `token_env` overrides discovery. |

These are built-in adapters; only `remote` requires a separate provider service. A future external-runner registry/dispatcher can implement that protocol without adding runner registration or long polling to Pulse.

All cloud adapters work in the default distroless image. See [cloud authentication](cloud-authentication.md) for environment variables, mounted credential files, identity permissions, and refresh behavior.

### Local Docker capacity

Omitting `providers` (or setting it to an empty map) creates a provider named `docker`. In that case, targets without `launch_services` default to `[{name: docker, priority: 1}]`. See [the minimal Docker example](../examples/docker-default.yaml). Explicit provider maps and target service selections are preserved; invalid or unavailable configured providers do not silently fall back to Docker.

Pulse discovers the Docker socket in its core provider code, without invoking the Docker CLI. An explicit provider `socket` wins; otherwise Pulse uses a named `DOCKER_CONTEXT`, `DOCKER_HOST`, or the saved current context from Docker's configuration (`DOCKER_CONFIG` or `~/.docker`). The `default` context uses `DOCKER_HOST` when set, otherwise `/var/run/docker.sock`. With no selected context or host, Pulse uses Docker Desktop's `~/.docker/run/docker.sock` on macOS when present, otherwise `/var/run/docker.sock`. Socket symlinks are resolved so aliases share admission ownership. Selected contexts must use a local Unix socket; invalid or remote configurations fail instead of falling back to another daemon. Docker Desktop normally selects its `desktop-linux` context; a system `/var/run/docker.sock` symlink is optional ([Docker Desktop socket setup](https://docs.docker.com/desktop/setup/install/mac-permission-requirements/)).

Docker requires no `pulse-exec`, host filesystem sharing, or `helper` configuration. The controller can run on Linux or macOS; the executor image must match the daemon's Linux architecture. Pulse launches the supplied command directly and attaches its finite stdin before startup.

On native Linux Engine, Pulse automatically adds `host.docker.internal:host-gateway` to worker containers, using the daemon's gateway address rather than a hard-coded IP ([Docker host-gateway configuration](https://docs.docker.com/reference/cli/dockerd/#configure-host-gateway-ip)). On macOS, Docker Desktop, and identified Colima daemons, Pulse preserves the runtime's built-in host DNS: replacing it with the Linux bridge gateway can incorrectly target the VM instead of the outer host. Pulse uses the configured JobDB URL for discovery and claiming. For local Docker workers, it replaces a loopback hostname (`localhost`, a loopback IPv4 address, or `::1`) with `host.docker.internal`, preserving the scheme, port, and tenant path. For example, `http://localhost:9047/c2` becomes `http://host.docker.internal:9047/c2` only in the worker command. The controller logs both addresses at submission. Remote JobDB URLs and cloud/remote-provider commands remain unchanged.

On Linux Engine, JobDB must listen on a host interface reachable through the bridge gateway; a service bound only to loopback is not reachable that way. HTTPS certificates must be valid for the worker hostname. An `import supplied lease` failure with `HTTP status 0` means the c2j client failed to obtain a usable response while validating its supplied lease, before executing the recipe. Possible causes include DNS failure, connection refusal, a dropped connection, the ten-second renewal request timeout, TLS validation failure, or an unreadable/malformed response. Zero is a client-side placeholder, not a server HTTP status. The current c2j/JobDB error message hides the underlying transport error; it does not identify which of those occurred.

Omitted Docker capacity settings allow one default-sized job: `max_containers: 1`, CPU rounded up from `defaults.cpu`, and memory equal to rounded default memory plus scratch (at least Docker's 6 MiB container minimum) plus `per_container_memory_overhead` (default `256Mi`). The pool remains fixed at startup; jobs exceeding it are declined. Budgets exceeding daemon resources fail startup. Configure explicit CPU, memory, and container-count budgets for larger jobs or concurrency, reserving room for the host. See [the explicit Docker example](../examples/docker.yaml).

Admission charges the full committed allocations, including pending and uncertain starts. Idle resource usage does not create more capacity. The adapter serializes admission, verifies created container limits before starting, and rebuilds its accounting from Docker after a controller restart.

Startup logs the selected socket, checks Docker's reported capabilities, and probes enforcement when the daemon reports support. A disposable `alpine:3.21` container runs `/bin/true` without any host mounts. The image is pulled if absent and retained in Docker's cache. The probe runs during `check` too. If Docker rejects the limited probe, Pulse verifies the same probe starts without limits, warns, and continues. If both probes fail, startup reports both daemon errors. Missing reported limit capabilities also produce a warning.

In this fallback mode, CPU, memory, and swap limits are omitted. Admission still charges the requested allocations and enforces the pool's concurrency budget, but these charges do not bound actual workload resource usage. Containers record their enforcement mode in `pulse_docker_limits`, so restart accounting works for both constrained and unconstrained jobs. Scratch tmpfs sizing remains enabled. c2j independently enforces recipe timeouts and lease validity.

Scratch uses a bounded tmpfs at `/scratch` by default. For `M` usable execution memory, `S` scratch, and configured overhead `H`, host admission charges `M + S + H`. When enforcement is available, the container memory limit is `M + S`; c2j receives the requested memory and scratch separately, even when native limits round upward. There are **no disk quotas or disk-backed scratch guarantees**. The adapter uses Docker's native platform and binds each launch to a locally resolved image ID. Docker CPU/memory limits are described in [Docker's resource documentation](https://docs.docker.com/engine/containers/resource_constraints/).

Docker executor images need c2j and their recipe dependencies. c2j owns execution timeouts and process cancellation; Pulse applies no default container lifetime cap. Explicit `timeout_seconds` or future `start_before` constraints return `unsupported` because this adapter cannot enforce those extra policies independently. Already-expired starts are rejected. Other clients must not restart or change managed containers outside this accounting. When several controllers need a host, put a single admission service behind the remote protocol.

### Cloud allocations and images

Cloud adapters select supported sizes internally during submission. Pulse builds executor environments from requested/defaulted resources and providers preserve them, even when native allocations round upward:

- Cloud Run supports the adapter's `linux/amd64` profile, rounds CPU/memory upward, and adds scratch to total container memory. Scratch is a bounded in-memory volume. See [memory combinations](https://docs.cloud.google.com/run/docs/configuring/jobs/memory-limits) and [in-memory volumes](https://docs.cloud.google.com/run/docs/configuring/jobs/in-memory-volume-mounts).
- ECS uses Fargate Linux platform `1.4.0`, supports `amd64` and `arm64`, and chooses valid task CPU/memory combinations. Usable scratch excludes image storage. See [Fargate storage accounting](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/fargate-task-storage.html).
- Azure uses consumption CPU/memory pairs and the associated ephemeral-storage capacity. It defaults to at most 2 vCPUs; set `max_azure_cpu_millis: 4000` only for an environment supporting those larger pairs. See [container resource combinations](https://learn.microsoft.com/en-us/azure/container-apps/containers) and [ephemeral storage](https://learn.microsoft.com/en-us/azure/container-apps/storage-mounts).

ECS and Azure require a deployment-supplied `image_storage_bounds` map for each **digest-pinned** image they can launch. Values are conservative, validated bounds for the image and provider overhead consuming task storage. The adapter subtracts that bound from provisioned storage to ensure it can guarantee the requested scratch. Unknown bounds or mutable image tags return `unsupported`; a configured number is an operator assertion, not an image measurement performed by Pulse. See [cloud configuration examples](../examples/clouds.yaml).

All cloud executor images need the updated `pulse-exec` helper to deliver lease stdin. Cloud Run and Azure default `supervisor_path` to `/usr/local/bin/pulse-exec`; ECS requires an explicit path and also uses the helper for execution timeouts. Cloud Run and Azure require an explicitly configured `defaults.timeout` for their native job limits and disable provider execution retries. ECS can omit a timeout; its bridge then applies no timer. This initial cloud implementation does not enforce queued start deadlines or working-directory overrides outside ECS; requests for those options decline rather than silently dropping them. Configure image access and workload credentials in the target deployment; per-job Azure registry/identity customization is not currently exposed.

## Lease transport

Executor images must support `c2j run with-lease --lease-file -`. Pulse pins the integration API to c2j v0.0.65 and JobDB v0.0.28. Deploy a matching or compatible c2j binary and a JobDB server supporting authoritative supplied-lease renewal. The verified Colony base image includes c2j 0.0.65 with execution-tool support for addon jobs.

Remote providers receive an optional sensitive `process.stdin` field and must pipe it to the child exactly, then EOF. Upgrade existing provider implementations before deploying this controller. Unsupported stdin must produce a definite decline before side effects; silently dropping it is invalid.

Docker streams the finite input through its native attach API and closes stdin; the capability is absent from container environment variables and arguments. Cloud native APIs transport the finite input in reserved `PULSE_EXEC_STDIN`. The updated `pulse-exec` removes that value from the child environment and delivers it through a private stdin pipe. The capability never appears in c2j arguments, Pulse diagnostics, or public instance lists. It remains visible in native container/task configuration to infrastructure principals with inspection access; protect those records like credentials and include them in your retention policy. This transport is not a secret-store integration. Keep broad JobDB discovery/claim credentials on the controller; do not add them to executor images or environments.

## Submission attempts

Pulse calls each selected launch service once per attempt and does not retry uncertain submissions. Providers perform one native launch attempt; optional native idempotency safeguards do not imply a replay or recovery requirement. If work is lost or fails to start, the supplied lease must expire before Pulse can claim a fresh attempt with a new ID. Definite non-starts release the lease with backoff; accepted and uncertain starts retain it. `accepted` reports admission or handoff, not guaranteed execution. The protocol imposes no durable submission journal, stored decline decisions, or fixed terminal retention. Built-in safeguards such as Docker's deterministic names and capacity reconstruction remain implementation choices.

Prefer prompt handoff to native compute. Deliberate provider-owned runner queues require a startup deadline; native scheduling and image-pull delays alone do not. When `start_before` is explicitly supplied, its actual-start constraint must still be enforced or declined as unsupported. See [submission and recovery semantics](../REMOTE_PROVIDER_PROTOCOL.md#submission-attempts-and-recovery).

## Active instances and retention

Every launch carries the complete jobdb instance/tenant/job/launch correlation envelope. Docker stores it in labels; Cloud Run stores it in annotations and container environment; ECS stores tags/environment; Azure stores tags/environment; remote services attach it to native resources or provider-owned queue entries. The process environment also exposes `PULSE_*` identity values.

The [public HTTP API](http-api.md) lists active instances through every configured provider. Lists include queued/starting/running work and exclude terminal instances; paused/stopping compute is included where reported. Only Pulse-managed native resources are returned, within each configured provider's scope. A service can show launches made before Pulse restarted or by another controller using the same scope. Duplicate configurations pointing at the same native scope can show the same resource under both provider names.

| Provider | Listing source and scope |
| --- | --- |
| Remote | `GET /v1/launches`, scoped to the provider endpoint and authenticated principal. Includes accepted queue entries before native assignment. |
| Docker | Labeled containers on the configured daemon. Created/restarting containers are `starting`; running/paused/removing map to `running`/`paused`/`stopping`. Exited/dead containers are excluded. Reads do not update admission accounting. |
| Cloud Run | Executions across jobs in the configured project/region. Pending executions are `starting`; a positive running task count is `running`. Completion/deletion timestamps or terminal completion conditions exclude an execution. Requires `run.executions.list`. |
| ECS | `ListTasks` for the configured cluster with desired status `RUNNING`, followed by `DescribeTasks` including tags. Provisioning/pending/activating tasks are `starting`; running tasks are `running`. Stopped tasks are excluded. Requires `ecs:ListTasks` and `ecs:DescribeTasks`. |
| Azure Jobs | Jobs in the configured resource group, then execution pages for managed jobs. Processing executions are `starting`, running executions are `running`; terminal statuses or end times are excluded. Requires read access to jobs and their executions. |

Cloud APIs can briefly lag acceptance or state changes. In particular, an accepted native start operation may not yet have an execution to list. Cloud Run and ECS pages can be empty after filtering while still carrying a continuation token. Azure walks nested job/execution pages with a stateless cursor; large inventories may need several requests. Docker sorts current container IDs and uses a last-seen-ID cursor. These are changing views, not historical or transactional snapshots. An empty list does not prove a past submission never ran or free capacity is available.

Docker worker containers use `AutoRemove: true`: Docker deletes them after exit, whether execution succeeds or fails, including after Pulse stops. Their local Docker logs disappear with them; c2j results and artifacts already persisted to JobDB remain available. Container-based launch deduplication lasts only while the container exists; the supplied JobDB lease still prevents a completed c2j job from running again. Containers created by older Pulse versions, per-launch cloud jobs, and ECS task-definition revisions require manual cleanup after your retention period. Abandoned Docker `created` containers remain charged until their outcome is inspected and they are safely removed. Host disk availability, image cache size, and retained logs remain operational concerns; there is no disk-capacity guarantee from Docker admission.

Controller restarts preserve ownership in JobDB. A late container must validate its supplied lease; an expired or superseded capability cannot claim replacement work. Late startup can still consume compute, and application side effects still need their normal idempotency under lease loss.
